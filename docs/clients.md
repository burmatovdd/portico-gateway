# Подключение клиентов

Доступ к моделям и доступ к MCP настраиваются отдельно. Инструкция Open WebUI относится к интерфейсам версии 0.11.3; названия пунктов могут отличаться в других версиях. Наличие настроенного подключения не подтверждает успешный OAuth-вход.

## Open WebUI: модели

Настроить вход в сам чат через IdP. Callback OIDC Open WebUI: `https://chat.example.org/oauth/oidc/callback`. Адрес возврата после выхода, если используется, также должен быть разрешён в IdP.

Создать серверное подключение OpenAI API к `https://portico.example.org/v1` либо внутреннему Service models. Включить `system_oauth`, оставить статический API key и Model IDs пустыми. Этот режим передаёт access token пользователя из сессии чата. Audience должен соответствовать `models.config.audience`.

Отключить общий кеш базовых моделей. Если права на модели полностью делегируются Portico через `BYPASS_MODEL_ACCESS_CONTROL=true`, сначала отключить прямые подключения к LiteLLM и другим провайдерам. Иначе обход локальных правил чата может расширить доступ. Сохранённая конфигурация Open WebUI может иметь приоритет над переменными окружения; проверить эффективные настройки.

Автоматическое применение этих настроек init-контейнером в отдельном инфраструктурном чарте не входит в чарт Portico. При установке официального Open WebUI настройку выполняет его администратор.

## Open WebUI: инструменты

### Регистрация в Portico

```yaml
config:
  oauth:
    clients:
      - id: openwebui
        token_endpoint_auth_method: client_secret_post
        client_secret_env: PORTICO_OPENWEBUI_CLIENT_SECRET
        redirect_uris:
          - https://chat.example.org/oauth/clients/mcp:portico/callback
```

Секрет задаётся через `oauthClientSecrets` и Kubernetes Secret. Это секрет MCP-клиента, не секрет приложения Casdoor. Callback зависит от ID подключения `portico`.

### Настройка администратором чата

Открыть административный раздел «Инструменты → Интеграции» и добавить подключение:

| Поле | Значение |
| --- | --- |
| Тип | MCP Streamable HTTP |
| Имя / ID | Portico / `portico` |
| URL | `https://portico.example.org/mcp` |
| Вход | OAuth 2.1 Static |
| Client ID | `openwebui` |
| Client secret | Секрет зарегистрированного MCP-клиента |
| Scope | `mcp` |
| Resource | Automatic |

Сохранить регистрацию клиента и подключение. Динамической регистрации на стороне Portico нет.

В «Контроле доступа» выбрать нужных пользователей либо **Public** с правом чтения для всех пользователей чата. В Open WebUI 0.11.3 пустой `access_grants` означает доступ только администраторам. Видимость подключения не заменяет проверку групп Portico.

### Вход пользователя

В новом чате открыть меню инструментов и выбрать Portico. Подтвердить подключение и пройти вход в IdP. Информационное окно «Доступные инструменты» показывает состояние, но не запускает авторизацию. Для повторной попытки использовать меню подключения инструментов. Старый callback повторно не открывать: OAuth-коды одноразовые.

Сначала проверить список инструментов и операцию чтения, например `strix__listReports`, если она зарегистрирована. Подтверждением служит ответ инструмента, а не текст модели. Выход из чата не гарантирует отзыв MCP-сессии; для текущей сессии предусмотрен `portico_logout`.

## OpenCode: только MCP

Пример конфигурации:

```json
{
  "mcp": {
    "portico": {
      "type": "remote",
      "url": "https://portico.example.org/mcp",
      "oauth": {"clientId": "opencode", "scope": "mcp"}
    }
  }
}
```

Запустить `opencode mcp auth portico`. Для клиента с callback `http://127.0.0.1:19876/mcp/oauth/callback` этот адрес регистрируется в Portico. Проверить фактический callback установленной версии OpenCode. Клиент создаёт локальный обработчик сам; отдельный пользовательский скрипт не требуется.

Это Authorization Code с PKCE, не Device Code. Доступ OpenCode к модели настраивается отдельно. Пример не подтверждает тестирование на всех ОС. Корпоративный CA должен быть доверенным в окружении клиента.

## Другие клиенты

Для инструментов требуются MCP Streamable HTTP, Authorization Code с PKCE S256, поддержка OAuth metadata и обновления токенов. Поддержаны методы `none`, `client_secret_post`, `client_secret_basic`. Серверные секреты не распространяются в пользовательских CLI. Каждый новый клиент проверяется по [сценарию приёмки](verification.md).
