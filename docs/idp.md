# Настройка провайдера идентификации

## Приложения и идентификаторы

Одна организация пользователей может обслуживать несколько приложений. Для независимого управления секретами и callback рекомендуется отдельное приложение IdP для чата и отдельное — для Portico.

| Настройка | Назначение |
| --- | --- |
| `config.oidc.client_id` | Приложение Portico в IdP |
| `config.oidc.audience` | Ожидаемый audience access token для core и целевого API |
| `models.config.audience` | Ожидаемый audience JWT клиента моделей, например приложения Open WebUI |
| `config.oauth.clients[].id` | Регистрация MCP-клиента внутри Portico, а не приложение IdP |

В IdP для Portico зарегистрировать `https://portico.example.org/oauth/callback`. Callback MCP-клиента чата регистрируется в Portico: `https://chat.example.org/oauth/clients/mcp:portico/callback`. Эти адреса не взаимозаменяемы.

## Требования к OIDC

Core использует Authorization Code, PKCE S256 и scopes `openid`, `profile`, `offline_access`. IdP должен выдавать ID token, подписанный JWT access token и поддерживать согласованный механизм refresh. Device Authorization Grant не является частью текущего основного MCP-входа.

Проверяются подпись, issuer, audience, subject, время выдачи и срок действия. При входе дополнительно проверяются nonce и совпадение пользователя в ID/access token. Поддерживаются RS256 и ES256. Opaque access token не поддерживается. Endpoints discovery должны удовлетворять проверкам origin в реализации; совместимость с новым IdP проверяется отдельно.

## Casdoor: группы и повторный вход

1. Создать организацию, например `example`, группу `red-team` и назначить пользователю членство.
2. Приложения чата и Portico связать с этой организацией. При изменении организации проверить привязку обоих приложений.
3. Включить Authorization Code и Refresh Token. Заполнить точные callback URL.
4. Обеспечить claim `groups: ["example/red-team"]`. Для models с `organization: example` обязателен подписанный `owner: example`. При JWT-Custom включить соответствующие поля. Формат групп — полный идентификатор, если именно он указан в политике.
5. Для core задать `roles_claim: groups`, `roles_format: strings` и разрешённые группы в `config.services.<service>.roles`. Название поля `roles` сохранено в схеме, хотя его значения могут быть группами.
6. Для повторного использования браузерной сессии проверить Signin session и Auto signin в используемой версии Casdoor. Автоматический вход требует существующей сессии той же организации.
7. Если самостоятельная регистрация не предусмотрена, отключить Enable signup. Успешный вход не должен автоматически выдавать административную роль.

Для Casdoor roles в формате объектов core поддерживает `roles_format: casdoor`, сопоставляя owner/name. Models ожидает массив строк в claim, указанном `groups_claim`.

Изменение групп не меняет уже выпущенный JWT. Повторный вход или refresh должен выдать актуальные claims. Немедленный отзыв всех JWT и единый backchannel logout не реализованы.

## Проверка

Проверить обычного пользователя с разрешённой группой и пользователя без неё. Администратор чата не получает доступ к модели или инструментам автоматически. Для нового IdP проверить вход, подпись, audience, nonce, refresh, истечение и выход. Совместимость по названию протокола без этих проверок не считается подтверждённой.
